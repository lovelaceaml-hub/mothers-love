## Correction round 1

The coordinator's review accepted three findings against the first pass. All three are fixed; no core, renderer.css, or renderer.html change was needed for any of them.

1. **MAJOR, peacemakers bubbles never retired.** The first pass's `registerScene(8, ...)` omitted `replaceMode`, so the Plan 15 core's `tickSlots()` (which only retires a steady bubble when the scene descriptor declares `replaceMode`) never retired one, while production always does for scene 8 (`tickSlots()`, `S.s===9?'hearts':'drift'`, so `'drift'` for scene 8). Fixed by adding `replaceMode: 'drift'` to `peacemakers.js`'s `registerScene()` call. Peace in Practice already had `replaceMode: 'hearts'` from the first pass; that part of the finding did not apply to it. Added a new spec, `a steady bubble retires by drifting out, then a new bubble arrives`, that steps past the first floater's 17 s `retireAt`, asserts a `bubble_exit_start` log entry for scene 8 with `kind: 'drift'`, then steps further and asserts a `bubble_new` log entry follows.
2. **MAJOR, long-message layout differed from production.** Production's `rightBubbles()` (`.tv17/prod/renderer.js` lines 159 to 164) shows a single record alone in one large reader slot (`readerSlot(long,861,37,925,586)`) whenever any of the four chosen records fails `smallFits()`; otherwise it maps the four chosen records straight to `ps[i]` in pick order. The Plan 15 core's `rightBubbles()` (`core/orbs.js`) always draws four bubbles through `drawSlots()`, which sorts positions by size and can therefore assign a different record to a different `ps` slot than production would, a Plan 15 decision-10 behavior for the other, approved scenes that production does not apply here. Fixed by adding a scene-local function to each file, `peacemakersRightBubbles()` in `peacemakers.js` and `peaceInPracticeRightBubbles()` in `peace-in-practice.js`, each copying production's `rightBubbles()` body exactly using the core's already-global `choose`, `smallFits`, `readerSlot`, and `addOrb`. Neither function is named `rightBubbles`, so neither shadows the core's global one. Both scenes' `markup()` functions now call their own scene-local function instead of the core's global `rightBubbles()`. Added two specs to each file: `a long message is shown alone in one large reader slot about 586 px wide` (a fictional 300-character message) and `with all-short records, four bubbles appear in pick order at production's ps positions`.
3. **Tests: the "click does not advance" test could not fail.** `loadRenderer` boots the runtime with `source: 'sample'`, and `manualAdvance()` returns early unless `S.source === 'live'`, so the assertion could never observe a failure. Dropped this test from both spec files. Added a new, meaningful spec to each, `every steady bubble stays outside the keep-out box, expanded by its radius, after 20 s`, using production's own collision formula (`core/motion.js`'s `steerOutside()`: `rad = d * depth * .49 + 14`) against each scene's `keepOut` box.

While writing the new long-message specs, the shared `circularity()` helper's `count` (which matches `.orb-slot, .orb, .event-orb`) was found to legitimately return 2 for a single bubble, since the bubble is both an `.orb-slot` wrapper and a nested `.orb`. The first draft of both new specs asserted `count === 1` and failed; corrected to `toBeGreaterThan(0)`, matching every other circularity assertion in both files. This was a test-only mistake, not a scene defect.

## Limitations / deviations

- First pass: two of my own test assertions needed adjustment after first-pass failures, both fixed within this lane's own spec files (no scene code changes were needed for either):
  1. The default `buildActiveDisplayFixture()` fixture used by `loadRenderer` carries only one recognition record, so the bubble-picking function (which needs 4 distinct records) only filled one bubble. Fixed by building a 6-record fixture (`manyRecordsFixture`) for the relevant tests in both spec files.
  2. Peace in Practice's ambient hearts use `heartSVG()`, whose markup includes an SVG `<defs><radialGradient>` block for the fill gradient (identical to production). `<defs>` content never paints, but Chromium's `scrollHeight` still accounts for its non-visual internal geometry, so the shared `noOverflow()` helper (raw `scrollHeight` compared to `clientHeight`) reported a false-positive 16 px overflow that traced to a `<defs>`/`<stop>` element, not to any visible pixel. Verified directly that every actual `.floating-heart` div renders well within the scene bounds (max bottom about 421 of 636 at 1920 wide). Replaced the generic `noOverflow()` check in `peace-in-practice.spec.ts`'s first test with a bounding-rect check scoped to the scene's actually-visible elements (`.scene-copy`, `img.art`, `#heart-host`, `.floating-heart`, `.orb-slot`), which passes and is not a false positive.
- Round 1: the `circularity()` count-equals-1 mistake noted above, corrected before this round's tests were reported as passing.
- The "pick order at ps positions" specs compare bubble positions with a tolerance (under 180 px) rather than an exact match, because `loadRenderer`'s own scene switch already steps the runtime forward once to skip the entrance transition, so some floater drift has already happened by the time the test reads state. The four `ps` slots are hundreds of pixels apart, so this tolerance still clearly distinguishes correct pick-order placement from the wrong, size-sorted placement `drawSlots()` would have produced.
