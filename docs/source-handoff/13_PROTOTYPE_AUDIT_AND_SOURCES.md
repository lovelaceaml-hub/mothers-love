## 4. Official technical references

Reviewed for this package on September 7, 2026. Recheck before implementation; no exact package versions, service prices or security certification are established here. The requirements are project proposals, informed by these primary sources.

### S01 — Codex project instructions

OpenAI, **Custom instructions with AGENTS.md**: https://developers.openai.com/codex/guides/agents-md  
At review, this redirected to https://learn.chatgpt.com/docs/agent-configuration/agents-md.

Codex documents reading AGENTS.md guidance before work and combining project/global instructions. Keep the supplied root instructions concise and use explicit file references. Do not overwrite existing project guidance blindly or assume every detailed spec is automatically loaded.

### S02 — Moving and auto-updating content

W3C, **Understanding SC 2.2.2: Pause, Stop, Hide**: https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html

This informs the proposal for effective pause/stop controls over automatic motion and updates. The handoff does not certify WCAG conformance. Our Still/Quiet design must be evaluated across actual animation mechanisms and the TV's operating context.

### S03 — Database authorization

Supabase, **Row Level Security**: https://supabase.com/docs/guides/database/postgres/row-level-security  
Supabase, **Securing your data**: https://supabase.com/docs/guides/database/secure-data

These distinguish database grants and row-access policies. Sensitive columns and exposed views need deliberate handling, not assumptions that a hidden UI field is protected. Tests must cover allowed and denied roles/operations.

### S04 — Client and server keys

Supabase, **API keys**: https://supabase.com/docs/guides/getting-started/api-keys

Use the currently documented publishable/client and elevated server key model when implementation is authorized. Elevated secrets must never appear in the TV browser, user-facing app, source control or chat. A publishable key is not an admin/user identity credential.

### S05 — Realtime authorization

Supabase, **Realtime Authorization**: https://supabase.com/docs/guides/realtime/authorization

The display's realtime access requires its own authorization design. Do not assume an authenticated-looking browser or a table policy automatically makes every channel/private payload safe. Choose and test the actual transport architecture later.

### S06 — Backups and restore

Supabase, **Database Backups**: https://supabase.com/docs/guides/platform/backups

Backups preserve previous database states for recovery. The actual provider/plan retention and restore behavior must be documented separately from the application's seven-day live-record policy. No pricing/plan guarantee is made in this handoff.

### S07 — Safe rendering of user content

OWASP, **Cross Site Scripting Prevention Cheat Sheet**: https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html

This informs the safe-output requirement: member content should remain text and must not become executable markup through template interpolation.

### S08 — Sensitive information in logs

OWASP, **Logging Cheat Sheet**: https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html

Logging design must avoid unnecessary sensitive data and credentials. Keeping personal text out of request/error/analytics logs supports the campaign's short content lifetime.
